# General-work contract — plan revision 4

Status: required implementation/qualification scope, not a claim that these capabilities are already shipped. The user authorized this milestone amendment on 2026-10-02. Boreal is a general work manager; software is one supported work domain. Keep the existing Rust authority and local-core release boundary.

## Product shape

Project is the authority/namespace; milestones group outcomes; direct tasks are executable units. Preserve the current legacy sprint hierarchy while completing the already-planned separation of scheduling cycles from decomposition. A cycle does not own task identity. A task can have no dates and no file outputs. Research, creative, administrative, software and mixed tasks use the same lifecycle; do not create separate state machines for work types.

A task carries a description, context references, prerequisite edges, optional deliverable requirements, a pinned acceptance profile and optional scheduling/wait metadata. Claiming is distinct from doing, submitting, accepting and closing. A chat/worker is an executor, not the durable work record.

## Existing foundations to reuse

At reviewed source 7b56cca, WorkItem and templates already contain description; template items contain dependency keys, labels, dispatch and focused/reviewed profiles. SourceVersion already identifies immutable bytes with media type, size, digest and availability. Production schema retains due_at; WorkSchedule includes not-before/due/planned windows and Intake has revisit_at. Existing profile storage pins requirements, and the receipt system already protects attempts/revisions. Do not replace these engines or infer shipping status from proposed spec documents. Qualify actual routes and schema migrations.

## Required model and behavior

1. **Optional output contracts.** A stable requirement key names purpose, required/optional status, allowed type/media, minimum/maximum count and bounded typed criteria. Empty declarations preserve old task behavior. A path glob alone is not an accepted artifact. Labels may describe a work domain; they never change authorization or completion semantics.
2. **Produced output identity.** Associate immutable artifact/source versions with the producing task/attempt, requirement key and submission. Record digest, media type, byte count, availability and provenance; maintain metadata separately from bytes. A captured file is not automatically approved, published or delivered.
3. **Accepted inputs.** Bind exact brief/source/asset versions, their role and access scope. Downstream work consumes an accepted result version, not whichever file is newest at a mutable path. Required context must be available before execution; optional unavailable context is disclosed. No uncontrolled whole-project context dump.
4. **Typed proof.** Preserve command execution receipts, and add attributable artifact validation and explicit decision/review evidence. Do not synthesize an executable, exit code or trusted execution attestation for a human approval. Distinguish producer assertion, automatic inspection and independent/operator acceptance.
5. **Adjustable rigor.** Registered versioned profiles may allow lightweight completion, validated deliverables, reviewed artifacts or software verification. Freeze supported names/meaning at S12-T01; old focused/reviewed profiles retain their contract. Selecting a weaker profile after publication requires explicit audited amendment, never an incidental edit or runtime fallback.
6. **Coverage and acceptance.** Required outputs must meet format, count, availability and revision criteria. Optional missing outputs are visible but nonblocking. Structural image validation does not prove design quality. Review names the exact artifact set and requirement/input revision. Stale/rejected/missing evidence must not pass close.
7. **Changes and lineage.** Preserve all old attempts, files, reviews and accepted results. A changed master or brief surfaces affected consumers and explicit revalidation/replan options; it must not silently retarget outputs, retroactively rewrite approval or automatically invalidate unrelated work. Requirement edits during a claim are fenced and versioned.
8. **Artifact portability.** Reuse the content-addressed source/blob store. Support binary files without requiring text extraction; bound size, count, parsing and materialization. Verify digest/size after restart or movement to another allowed root. A temporary absolute path is not a portable identity. Missing or denied bytes stay explicit; no claim of full recovery from a database-only backup.
9. **Safety and rights context.** Project/access scope applies to input and output reads and exports. Prevent traversal/symlink escapes and treat filenames, source text and archive entries as data. Never execute embedded instructions. Record attribution/rights provenance where the task requires it; the system does not invent legal clearance. Do not place credentials, private keys or payment details into task evidence or diagnostics.
10. **Dates.** Keep due date, planned start/end, not-before and follow-up/revisit separate. All remain optional. Use existing civil-time/timezone rules; test date-only values, midnight and DST. Agent heartbeat, lease, retry delay and hard execution deadline are not business scheduling fields.
11. **External waits.** A structured wait records what is needed, an accountable person/role/service, dependent work, follow-up date, state and attributable resolution. Resolving a wait does not complete its task. Time passing, a reminder or agent text never supplies an approval. Block only affected work; unrelated ready work continues.
12. **Recurring operations.** Preserve existing cycle-series/carry-over semantics. Repeated orders, support cases or research requests receive fresh work identities and refer back to the versioned template/source request; do not reopen a completed task as if it were a new order. Automated external webhook/CRM/payment orchestration remains a future adapter, not a release requirement here.
13. **Templates.** Parameterized modules compile into a concrete validated project-local DAG before publication. Preserve stable IDs and add only supported fields/capabilities. No arbitrary executable condition language. Retry-safe template application must not duplicate work. Current admission is 1–100 items; this build plan has exactly 100. This is not a universal workflow-language rewrite.
14. **One interface contract.** CLI, service, agent guide and TUI invoke the same Rust operations. Show inputs, outputs, selected rigor, waits, dates and precise missing acceptance requirements. No client-owned status or direct TUI database writes. Unsupported old-store capabilities return actionable errors.
15. **Visual planning.** Extend the current project TUI, not a second web application. Show hierarchy separately from scheduled cycles, dependencies/readiness and optional date views. Make artifact details and missing/denied/stale states inspectable. Preserve keyboard/narrow-terminal usability, cancel/back/retry and conflict recovery.
16. **Bounded concurrent execution.** Retain claims, fences, idempotent operations and accepted dependency closeout. One owner per shared whole file; nested workers receive disjoint assignments. A waiting human decision need not retain a live agent lease. Never use Operator identity to make an enrolled-worker test appear to pass.
17. **Migration and recovery.** Additive schema/version negotiation preserves legacy task descriptions, dependencies, attempts, profiles, evidence and dates. Old exports/clients either round-trip supported fields or reject with explicit limitations; they must not silently drop required outputs. Include blob retention, missing-byte diagnosis and rollback compatibility in existing recovery tests.
18. **End-to-end proof.** An ordinary enrolled agent must complete lightweight research and a brief/logo/variants/landing-page chain, including one real rejection/revision, through supported operations. Tests cover missing outputs, wrong formats, optional outputs, changed inputs, stale review, restart, file relocation and a resolved external wait. No live provider account, bank or payment is required for these synthetic local fixtures.

## Ownership and integration

S12-T01 freezes shared contracts and capability fixtures. T02 owns work requirements/planning/template semantics and their persistence. T03 owns typed proof, selected rigor and close/review applicability. T04 owns accepted input/output artifact identity, source bytes and recovery. T05 owns callable CLI/service/guide parity. T06 owns headless mixed-work recovery. S13-T01 owns dates/waits, T02 owns general-work TUI and T03 owns reference templates/pilots. S12-T90 and S13-T90 join their lanes; S11 qualifies the installed product.

Existing whole-file grants take precedence. New module paths in packets are candidate seams; use current equivalents where appropriate, with one named steward for shared domain/store/protocol/CLI wiring. Schemas and migrations are integrated serially. Nested workers do not acquire independent write rights to the same file by choosing different line ranges.

## Boundaries

This milestone builds a local general-work manager that can run in a qualified cloud container. It does not build a hosted SaaS, custom MCP deployment, bank/payment provider automation, CRM, commerce engine or a particular business. The user's separate downloadable business V1 package is not committed by this amendment. Product templates used here are bounded validation fixtures.

Git planning records are not runtime status. Import/adoption does not publish, claim, approve, recover or complete work. Use supported current-revision operations and read-back, and retain unknown outcomes. No task acceptance is supplied by this document.
