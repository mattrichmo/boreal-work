# Validation playbook: correct evidence at the correct layer

## Ground rule

Creating this plan does not compile, test or accept the product. Existing archived logs may refer to different source bytes and fixture controllers. Every implementation task must produce its specified current evidence. A task that needs an unavailable tool/platform/reviewer remains blocked; no fabricated command output, receipt or peer identity is allowed.

## Evidence layers

| Layer | Valid use | Does not establish |
| --- | --- | --- |
| Static source/contract inspection | Invariants, drift, exact API/schema definitions and proposed checks. | Runtime correctness. |
| Pure unit/property inputs | Determinism, precedence, proof/context selection, invalid combinations and algebraic invariants. | Transaction/service/process/release success. |
| Store integration | Real migrations/constraints/transactions under controlled concurrency and negative corruption setup. | Authenticated service/TUI or genuine verifier execution. |
| Application/service integration | Built Rust service, authenticated requests, actual transactions, operation readback and external execution. | Native installed package or published-channel identity. |
| CLI/TUI real-service PTY | Actual public routes, terminal input/resize and service-authorized actions. | A fake controller or transformed DTO is not equivalent. |
| Native installed artifact | Absolute installed binary, assets, runtime/ABI and disposable project behavior. | Other target platforms or published bytes. |
| Published channel | Actual authorized publication, clean download/verification/install/readback. | Merely assembling a local ZIP. |
| Genuine agent/human workflow | Actual supported harness/model/operator follows trusted workflow without hidden parent guidance. | A script simulating an unfamiliar agent. |

Owned temporary negative setup may deliberately corrupt rows or inject a stale receipt to prove rejection. Label it as test setup and never present it as successful application-produced proof. Genuine passing proof must be generated by the declared verifier through the supported boundary with attributable command/source/environment/artifact identity.

## Standard interface for new production harnesses

New Python harnesses under the proposed `scripts/validation/production/` directory should offer `--help`, `--binary ABSOLUTE_PATH`, `--output DIR`, `--strict`, and a clear temporary-root selection such as `--temp-root DIR`. Specialized harnesses may add explicit target/workload/fault/clock arguments. Document their exact invocation and return nonzero for any required failed, skipped, unsupported or unavailable case in strict mode. Do not silently use a global `bwrk`, fake service or fixture-side DTO repair when `--binary` fails.

The harness writes machine-readable summary plus raw logs and per-case records. Include case ID, requirement/task, observed assertion, setup evidence class, source/binary/package digest, platform/runtime versions, clock policy, exit code, service operation/readback IDs and artifact hashes. Redact secrets. Use deterministic seeds and barriers for race reproduction where applicable; don't hope sleep timing happens to cover the race.

Failpoints must be test-only, scoped to a disposable service/project and unavailable to unauthenticated or production binaries. Test their exclusion in production packaging. Virtual clocks prove domain deadlines; actual process tests prove restart, stale authority and external resource disposition. Neither substitutes for the other.

## Required case families

Every relevant operation gets allowed, denied, stale revision, wrong project/principal, duplicate/different-payload operation ID, and deadline-boundary cases. Test late arrival before/after timeout, crash before/after commit, readback after reconnect, corrupt references, deleted/mistyped requirements, unrelated historical evidence, profile/source drift and old protocol clients. Unknown operation results cannot be labeled failed without the accepted registration/expiry semantics.

Concurrency includes competing claims, hold/dependency change versus claim, review/close/source change, override/reopen versus stale context, retention versus backup/publication, source indexing versus replacement, project switch versus late responses, and service writer fairness under heartbeats/readers. Record both queue wait and transaction hold, plus invariant audit at the end of each fault/soak run.

## Full product scenario

Build the binary, initialize two disposable isolated projects with overlapping IDs, authenticate separate principals and create one milestone/two cycles/four tasks with cross-cycle dependencies and different pinned profiles. Show queued/paused/retry/blocked/expiry/review/proof/complete/closed distinctions with secondary reasons and safe server actions. Run real execution/verification, required independent review, close intent and accepted closeout; prove only accepted closed unblocks. Exercise stop/release, safe expiry disposition, cancellation, reopen, carry-over, an audited force and a specific dependency waiver.

Index/cite an actual source; create and publish curated memory; recover interrupted publication and produce a cited handoff. Use CLI/JSON/TUI and actual agent harnesses. Verify project switching/unavailability, corruption quarantine, legacy import disposition, backup/restore and restore-epoch fencing. Repeat the relevant slice from absolute installed native binaries and published channels after qualification.

## Exact-source acceptance and reruns

A merge changes the evidence subject. Re-run impacted focused plus required integration gates on the combined tree; final qualification runs the complete strict matrix. Record old failures and new passes as distinct attempts. Do not move thresholds, normalize service output, silently drop a target or call an unavailable case passed. An explicitly outside-scope case may be documented as not applicable only with the accepted scope rationale.
