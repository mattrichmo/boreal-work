# Declared production release scope and priorities

## Must-have: final supported product

The release scope is the project-local, same-host Rust service and human/agent CLI/TUI product already intended by the repository. Supported macOS/Linux package targets must be explicitly fixed and exercised; the baseline target matrix is a source to verify, not proof current runners exist. The application includes project/workspace isolation, authenticated actors, decomposition/cycles, task dependencies, typed acceptance, attempts/resources, genuine evidence, review, accepted closeout, audited exceptions, derived statuses/rollups, source citation, curated memory, workflow guidance, v1 disposition/migration, maintenance/backup and installation/upgrades.

All 199 scoped tasks and 66 gates in this issue are mandatory for that declared product. A task may prove an existing implementation already correct and make no production change, but still needs its specified evidence and handoff. "Already has code" is not an acceptance category.

## Must-have safety and truth properties

Project identity cannot fall back silently. A caller role string is not authority. A stale fence cannot mutate execution state or permit premature resource reuse. Deleting a gate result cannot delete its requirement. Failed verification is not absent verification; rejected review is not pending review. Normal dependency waiting is queued, not a generic hard hold. Expiry recovery survives clearing an active pointer. Complete is not accepted closed. Cancellation is not default dependency success. Overrides preserve the unsatisfied raw fact. Offline views cannot authorize writes. Every unknown outcome has a documented readback resolution rather than guessed success or blind duplicate execution.

Corruption diagnostics must preserve valid work where safe without manufacturing counts. Canonical history and required artifacts remain available under declared retention policy. Migration never maps a legacy success-shaped word into trusted v2 acceptance without explicit evidence/disposition. Binary rollback never implies a safe database downgrade.

## Should-have hardening, included where needed for production

The scoped performance, retention, diagnostic export, path/credential security, load/fairness and support tasks establish a minimum operational floor. They are not optional merely because they are called hardening. Further optimization, richer observability and ergonomic polish beyond the accepted budgets can enter the later backlog. Numeric performance/resource budgets are decided in PF-S01, measured on declared hardware in PF-S17, and cannot be relaxed after a failure just to pass.

## Later improvements, not hidden launch requirements

Recurrence/templates, semantic retrieval improvements, predictive scheduling, broader nesting and dashboards may follow once the canonical local workflow is stable. They require separate proposals and IDs. No empty runtime stub or inaccurate help entry is needed to reserve them.

## Scope change policy

An owner may explicitly revise the product scope before implementation with a versioned decision, impact analysis, user-visible limitation and changed acceptance graph. That is a new agreed scope, not proof of the original full completion. Critical authority, integrity, isolation, proof, recovery or artifact-identity gaps are not waivable within a production-ready claim. Optional deferrals need an owner and follow-up, but never substitute for required native evidence or an independent review.

Publication, branch pushes, release tags, signing, registry changes and customer data migration require separate actual authorization. The planning request does not grant it.
